def busy_jobs():
    """Only the jobs with 3 runs or more (HAVING).

    WHERE picks rows before they are counted, so it can't test a count. HAVING tests each
    group after GROUP_BY has counted it.
    """
    return statement(
        SELECT(job_runs.job_id, AS(count_rows(), "runs")),
        FROM(job_runs),
        WHERE(between(job_runs.dt, FIRST_DAY, LAST_DAY)),
        GROUP_BY(job_runs.job_id),
        HAVING(at_least(count_rows(), 3)),
    )

Jobs with no runs, and jobs with at least one: anti-join and semi-join.

Why: a job missing from the runs is often the very problem you're looking for, and a plain JOIN can't show it, since JOIN keeps only the rows that match.

jobs_that_never_ran()

def jobs_that_never_ran():
    """Every job with no run on these days (in SQL, an anti-join).

    LEFT_JOIN keeps every job, and a job with no run gets NULL in job_runs' columns, so
    is_null(job_runs.run_id) keeps just those. The day bound goes in ON=, not in WHERE: in
    WHERE it would throw away the very jobs with no runs, whose dt is NULL too.
    """
    return statement(
        SELECT(jobs.job_id, jobs.job_name),
        FROM(jobs),
        LEFT_JOIN(
            job_runs,
            ON=all_of(equals(job_runs.job_id, jobs.job_id),
                      between(job_runs.dt, FIRST_DAY, LAST_DAY)),
            # A job has many runs. That is fine here: the jobs kept are those with none.
            many_matches=True,
        ),
        WHERE(is_null(job_runs.run_id)),
    )

jobs_that_ran()

def jobs_that_ran():
    """Every job with at least one run on these days, each job once (in SQL, a semi-join).

    A JOIN straight to job_runs would repeat a job once per run. So first make the list of
    job_ids that ran, each once, with SELECT_DISTINCT, then JOIN to that list.
    """
    ran = derived("ran", statement(
        SELECT_DISTINCT(job_runs.job_id),
        FROM(job_runs),
        WHERE(between(job_runs.dt, FIRST_DAY, LAST_DAY)),
    ))
    return statement(
        SELECT(jobs.job_id, jobs.job_name),
        FROM(jobs),
        JOIN(ran, ON=equals(ran.job_id, jobs.job_id)),
    )

Label with if_else, fill NULL with fill_null, count by condition, and divide.

Why: codes and NULLs make a result hard to read, and a count of each kind side by side gives one row per job instead of one row per job and status.

labelled_runs()

def labelled_runs():
    """Each run with a readable status and a length label (in SQL, COALESCE and CASE WHEN).

    A run still going has no status yet (NULL), which fill_null shows as RUNNING. if_else
    gives one value where its condition holds and the other where it doesn't.
    """
    return statement(
        SELECT(
            job_runs.run_id,
            AS(fill_null(job_runs.status, "RUNNING"), "status"),
            AS(if_else(more_than(job_runs.duration_mins, 20), "long", "short"), "length"),
        ),
        FROM(job_runs),
        WHERE(between(job_runs.dt, FIRST_DAY, LAST_DAY)),
    )

def outcomes_per_job():
    """One row per job, with a column for each outcome (a pivot).

    count_rows(where=...) counts only the rows where its condition holds, so each column
    counts one kind of run. A run still going is counted with is_null, since equals can't
    find NULL. A TEST run is in none of the three columns, so they needn't add up to the runs.
    """
    return statement(
        SELECT(
            job_runs.job_id,
            AS(count_rows(where=equals(job_runs.status, "SUCCESS")), "succeeded"),
            AS(count_rows(where=equals(job_runs.status, "FAILED")), "failed"),
            AS(count_rows(where=is_null(job_runs.status)), "still_running"),
        ),
        FROM(job_runs),
        WHERE(between(job_runs.dt, FIRST_DAY, LAST_DAY)),
        GROUP_BY(job_runs.job_id),
    )

failed_share_per_job()

def failed_share_per_job():
    """Each job's failed runs as a percent of its runs: one count divided by another.

    Divide after GROUP_BY, as one count by another, not an average of per-row values. Times
    100.0 for a percent; / keeps the decimals even between two counts, in Hive and Spark alike
    (DIV is the one that drops them). A division by 0 gives NULL, which pandas shows as NaN;
    COUNT(*) of a group is never 0, so it can't happen here.
    """
    return statement(
        SELECT(
            job_runs.job_id,
            AS(count_rows(where=equals(job_runs.status, "FAILED")) * 100.0 / count_rows(),
               "failed_percent"),
        ),
        FROM(job_runs),
        WHERE(between(job_runs.dt, FIRST_DAY, LAST_DAY)),
        GROUP_BY(job_runs.job_id),
    )

Build a Saved table: create it, write a day, add to a day, backfill, rebuild.

Why: a result that is slow to work out, or read by many notebooks, is cheaper to work out once a day and save than to work out again every time someone reads it.

A Saved table is written one day at a time, and each function below is one step. The Example database can't be written to, so the steps show their Hive but no result. At work, send each one with run(step(), send=run_query), run_query being your own send function, and loop over the ones that return a list.

def alerted_runs(day=LAST_DAY):
    """Step 3: add that day's runs that succeeded but raised a high alert.

    INSERT_INTO keeps the failed runs step 2 wrote, and adds these beside them. They come
    from a second table, run_alerts, which is why they are a second Statement rather than
    another condition in step 2. Send it once, after step 2. Sent twice, these runs would be in
    the day twice; to redo a day, send step 2 again first, which clears it.
    """
    return statement(
        INSERT_INTO(runs_to_review),
        # A run can raise several high alerts, so DISTINCT keeps each run once.
        SELECT_DISTINCT(job_runs.run_id, job_runs.job_id),
        FROM(run_alerts),
        JOIN(job_runs, ON=equals(job_runs.run_id, run_alerts.run_id)),
        WHERE(
            equals(run_alerts.dt, day),
            equals(job_runs.dt, day),  # the joined table's Date partition needs a bound too
            equals(run_alerts.severity, "high"),
            equals(job_runs.status, "SUCCESS"),
        ),
    )

def careless(many_matches=False):
    """What most people write first: it runs, and the Toolbox warns at the JOIN line.

    run_alerts has one row per alert, so each run is repeated once per alert it raised.
    careless(many_matches=True) pastes the Warning's opt-out, which silences it but still
    gives 150 minutes instead of 100.
    """
    return statement(
        SELECT(AS(sum_of(job_runs.duration_mins), "minutes"), AS(count_rows(), "alerts")),
        FROM(job_runs),
        JOIN(run_alerts, ON=equals(run_alerts.run_id, job_runs.run_id),
             many_matches=many_matches),
        WHERE(between(job_runs.dt, DAY, DAY), between(run_alerts.dt, DAY, DAY)),
    )

Table

A Table reference: a table's columns, the day column it's split by, and its key.

Its columns become attributes, so job_runs.status is checked when your script runs: a typo stops with the list of real columns. Write one per table, generated once by write_table_reference(...) and then yours to edit.

  • columns maps each column to its Hive type as DESCRIBE, the command that lists a table's columns, prints it ("bigint", "decimal(10,2)"), or None when you don't know it. A typed column gets its values checked.
  • date_partition is required: the one date column the table is partitioned by, which every Statement must bound at both ends, or None for a table that has none.
  • key lists the columns that pick out one row, the table's Key. JOIN warns when a join doesn't use all of them; a write into a Saved table with a Key is refused unless the Toolbox can see each row it writes has a Key of its own (help(INSERT_OVERWRITE) says how); and one Edition's create_table writes it into the table (help(create_table) says why the other leaves it out). Hive never checks it.
  • does_not_add_up lists columns that are averages, ratios or distinct counts, which sum_of(...) and average_of(...) refuse to add up.
  • date_format is needed only when the Date partition's days aren't written like "2026-09-25", for example date_format="%Y%m%d". It must put the year first, then the month, then the day: Hive compares the days as text, and only year-first text sorts in date order. The time zone is whatever the table uses; the Toolbox doesn't convert it.

A Saved table, one your Statements write into, also says how it is stored, which create_table writes and check_table_reference compares with the table. Of these, a Saved table needs only location; a table someone else owns has none of them:

  • location is the folder your Saved tables go in, such as "/data/your_team/tables". The Toolbox adds the table's own folder, its database and its name, so mart.daily_runs is at /data/your_team/tables/mart/daily_runs. Every Saved table is an external table: its files are yours, in that folder, and the warehouse only keeps a record of where. Two tables in one folder would read each other's files, so a Saved table whose folder would be another's, or inside another's, is refused.
  • purge=True makes dropping the table delete its files too. purge=False keeps them in its folder, where a table created again reads them back; left out, the warehouse's own choice, which keeps them, is neither written nor checked.
  • properties holds any other table properties, the notes on a table the warehouse keeps by name, such as {"made_by": "daily_pipeline"}.
  • stored_as is the file format, "ORC" (the usual one) or "PARQUET", and compression how its files are packed: "SNAPPY", or ORC's "ZLIB" or Parquet's "GZIP", among others.
  • partitioned_by lists Partitions after the Date partition, such as ["region"], each a column in columns too: each day's folder then holds a folder per region. A write still fills one day, and the regions inside it from its rows' values.
  • bucketed_by with buckets spreads each day's rows into that many files by the values of those columns, and sorted_by sorts the rows in each, so a join on them can pair file with file. Leave them out unless the table is big and joined on those columns: changing them means writing the table again.

A column whose name is a Python word, such as from, is reached with getattr(t, "from"). You never type backticks: the Hive puts a name in them where Hive or Spark needs it, such as from, any or two words, and leaves a plain name, such as dt, as it is.

FULL_JOIN

INSERT_OVERWRITE

Write the Statement's rows into one day of a Saved table, replacing that day.

It goes first, before SELECT. The day written is the one day the Statement reads, so loop over by_day(s) to write several. Columns are matched to the Saved table by name, and the Toolbox puts them in the table's order, leaving out its Date partition. Re-running a day replaces it rather than adding to it, so a day can safely be sent again; to add rows to a day instead, use INSERT_INTO. If your warehouse runs Hive 2.3 or 3.1 under Tez (ask whoever looks after it), a day that now comes back empty may keep its old rows (HIVE-18702). After editing a Saved table's Table reference, check it with check_table_reference(t, send=...).

When the Saved table's Table reference declares a Key, the write is refused unless the Toolbox can see that each row it writes has a Key of its own, since Hive never checks one: a GROUP_BY over the Key's columns, a SELECT_DISTINCT, a row_number(...) kept at 1 for each Key in a Derived table, or reading a table by its own Key, each join matching its joined table's whole Key. The day written is one value, so a Key that holds the Date partition needs only its other columns. unproven_key=True writes it anyway, for rows that are one per Key for a reason the Toolbox can't see. Below, GROUP_BY makes one row for each job_id.

A Saved table with partitioned_by=["region"] has Partitions inside each day: the write still names its one day, and fills each region from its rows' values, so SELECT must list region too. Filling a Partition from the rows needs Hive's dynamic partitioning switched on, the Session setting the Toolbox calls "dynamic_partitions", whose two SET lines show_hive prints ahead of such a write. Send them with run(hive_settings("dynamic_partitions"), send=send) before the first such write: the warehouse keeps them for as long as send's connection lasts, and sending them again does no harm.

rollup

Subtotals for GROUP_BY: dropping its columns from the right, to a grand total.

GROUP_BY(rollup(jobs.team, jobs.job_name)) gives the usual row for each team and job, as GROUP_BY(jobs.team, jobs.job_name) does, and as well, a subtotal row for each team, which totals over every job_name, so job_name is NULL in it, and the grand total, one row over all the rows, with team NULL too. window

The rows a calculation looks across for each row, passed to it as over=.

  • PARTITION_BY= makes the groups: each row looks only at the rows sharing its values. The word is SQL's, and has nothing to do with a table's Date partition. Left out, every row is in one group.
  • ORDER_BY= puts each group's rows in order, with descending(...) for largest first.
  • rows=(start, end) keeps only the rows near each one, counted from the row itself: negative before it, 0 the row itself, positive after it. None means no limit: every row before it as the start, every row after it as the end. rows=(-6, 0) is the row and the 6 before it; rows=(None, 0) every row up to it. It needs ORDER_BY. Left out, each row looks across its whole group.

PARTITION_BY and ORDER_BY take columns or a list of them, never a name given in SELECT. Each row keeps its own row, so a Window changes no row count, and needs no GROUP_BY. Hive can't test a Window's result in WHERE or HAVING of the Statement that works it out: work it out in a derived(...) table, and test it in the Statement that reads it. A Window over the totals of a GROUP_BY, such as each job's share of the day, goes the same way: total in a derived(...) table, and the Window in the Statement that reads it.

hive_settings

The SET lines of Session settings, by name, to send before your Statements.

Hive keeps a Session setting for the rest of the session, so send them first, then your Statements: run(hive_settings(...), send=...) sends each SET line as a call of its own, and gives back None. They hold only while your send keeps one session across its calls, as spark.sql does in one notebook: if each call of your send opens a new session, each SET is gone before your Statement runs. show_hive prints them, and export_lineage, passed them with the Statements, writes them at the foot of both its files.

Name one or more sets. The Toolbox ships four:

  • "dynamic_partitions": hive.exec.dynamic.partition=true and hive.exec.dynamic.partition.mode=nonstrict. For a table partitioned by more than its day, such as by region too: a write gives the day, and Hive fills the other Partitions from each row's own values only with these on.
  • "map_joins": hive.auto.convert.join=true and hive.auto.convert.join.noconditionaltask=true. Hive then joins a small table by copying it to every worker, which skips sorting the big one, and chooses this by itself from the tables' statistics.
  • "statistics_on_write": hive.stats.autogather=true and hive.stats.column.autogather=true. Each write then gathers the statistics of the day it writes, which Hive picks its join plans from, so they are never out of date.
  • "merge_small_files": hive.merge.mapfiles=true, hive.merge.mapredfiles=true and hive.merge.tezfiles=true. A write then merges its small files into fewer, larger ones, since many small files slow down every later read.

unchecked_hive

Hive you write by hand, for run to send when no clause function writes it yet.

No Guard, Warning or Load limit looks inside it: the Toolbox sends the text as you wrote it, dropping a ; you end it with, and can't tell whether it gives the right answer. admin.add_columns

Add the new columns of a Saved table's Table reference to the table itself.

It sends DESCRIBE through your send as it is made, and adds each column of the Table reference that the table doesn't have yet. So you add a column by adding its line to the Table reference first, after the table's other columns (its Date partition's line may stay last, as Partitions aren't among them): Hive adds new columns after the table's own, and a write fills a table's columns in their order. Then run the Statement it gives, with the same send. The rows already in the table read NULL in a new column until their day is written again. For a table with a Date partition it writes CASCADE: each day already there gets the new columns too. Without it, each of those days would keep its old list of columns, and a day written again would lose the new columns' values. Spark refuses CASCADE, so if Spark rather than Hive runs your tables, ask whoever looks after them first.

It refuses a table that isn't one of your Saved tables, a Table reference with no new column, a new column that isn't after the table's own, and a new Partition, which a table can't gain: create a new table with it, and copy the days in.

admin.drop_days

Drop a Saved table's days before a given day: an ALTER TABLE Statement.

Each day of the table before before, a datetime.date or a day written as the Table reference writes days, goes: every row of it, so no Statement reads it again. It is how a Saved table keeps only so many days, and does the job TRUNCATE can't: Hive refuses TRUNCATE on an external table, a table whose files are in a folder you give, and every table create_table makes is one. The days' files go too when the table has external.table.purge true, which purge=True in its Table reference asks for (help(admin.drop_table)); otherwise they stay in the table's folder. It refuses a table with no Date partition, and one that isn't one of your Saved tables.

Hive takes a comparison such as dt < '2025-01-01' in DROP PARTITION, so one Statement drops them all. Spark takes only = there, one day at a time, so Spark refuses this Statement: if Spark rather than Hive runs your tables, ask whoever looks after them. The Example database, which is never written to, doesn't run it either.

admin.drop_table

Drop one of your Saved tables: the DROP TABLE IF EXISTS Statement.

The warehouse forgets the table, and every Statement that reads it fails until it is created again. Whether its files go too is up to the table itself: they go, every day of it, when the table has external.table.purge true, which purge=True in its Table reference asks for. create_table writes it into the table it makes; for a table made before you gave its Table reference purge=True, send admin.set_properties(t) first. Otherwise the warehouse only forgets the table: its files stay in its folder, and a table created there again reads them back. It refuses a table that isn't one of your Saved tables, a Table reference with no location=, such as job_runs, which others fill.

The usual reason is a change to a Saved table's columns that admin.add_columns can't make, such as removing or renaming one: drop the table, create it again, and write its days again, with purge=True set in the table first, or the old days come back. admin.move_to_own_folder

Move a Saved table to a folder of its own: a list of Statements to run.

A Saved table belongs in its own folder, under its Table reference's location=: in a folder it shares, two tables read each other's files, and an INSERT OVERWRITE of a day in one can delete the other's files for that day. This sends DESCRIBE FORMATTED and SHOW PARTITIONS through your send to find where the table is and which days it holds, and returns the Statements that move it, to send in order with run, one at a time:

  • create a copy, named like the table with _moving added, at the folder the Table reference gives the table, its own, stored as the Table reference says;
  • copy each day into it with INSERT OVERWRITE, one Statement for each day;
  • compare each day's rows in the two, and stop the move, before anything is dropped, if any day differs or is missing from the copy, such as one written since the steps were made;
  • set external.table.purge to false on the old table, whose folder may hold other tables' files, so that dropping it leaves them. A managed table, one whose files the warehouse keeps where it chooses, as create_table made them before 5.0, skips this step: its files are its own, and go with it;
  • drop the old table;
  • give the copy the table's name: its files stay at its own folder.

So a table with two days takes seven Statements, moves[0] to moves[6]. Each can be sent again until the old table is dropped: if one fails, fix what it says, and send them again from the first. Rows with no day aren't copied, and go with the old table. The rows are copied as the old table reads them, so where two tables shared a day's folder, each read the other's rows too: check them first, or write the days again from their source instead. It refuses a table that isn't one of your Saved tables, one already at its own folder, and one that lacks a column of its Table reference. The Example database is never written to, so it doesn't run the steps.
