# Copilot files for sqlglot Composer 8.2: start here

**Read this file to choose the one Copilot file your task needs, then follow the steps below
in order.**

sqlglot Composer 8.2 writes Hive, the SQL of the user's warehouse, from Python. You build a Statement from Clause functions, such as
SELECT, FROM and WHERE, and the Toolbox writes its Hive and refuses one that would give a
wrong number or read too much. These files teach Microsoft Copilot to write that Python, so
you can ask it in plain words.

## Terms

- **Copilot file**: one of the files in this folder; each teaches Copilot one objective.
- **Statement**: one query, built in Python with `statement(...)`, that becomes one string of
  Hive.
- **Project**: your folder at work holding the Toolbox and your own code.
- **Table reference**: the file in your Project's references/ folder that describes one
  table: its columns and their types, its partitions and its Key.
- **Saved table**: a table in the warehouse that your own Statements write.
- **Refusal**: the Toolbox's message when it won't write a Statement's Hive.
- **Workflow**: the steps to one end goal, such as converting Hive, each a cell of the
  Workflow's notebook in admin/workflows/.

## Steps

1. **Choose the file.** Goal: the file that teaches Copilot your task. Action: find your
   task under Which file. Done when you have one file, or for an Excel workbook three, as
   the Decision rules say. Then step 2.
2. **Open a chat.** Goal: a chat holding nothing from another task. Action: open a new chat
   in Copilot. Done when the chat is empty. Then step 3.
3. **Load the file.** Goal: Copilot reads the file first. Action: paste the file as your
   first message, and send it. If a paste is cut short, attach the file instead. Done when
   Copilot has the file. Then step 4.
4. **Ask.** Goal: Copilot knows your tables. Action: say which tables to read: paste each
   one's Table reference, its file in your Project's references/ folder, or say its import
   line and columns, such as: `from references.ops__job_runs import job_runs` gives
   ops.job_runs: run_id bigint, job_id bigint, status string, dt string; partitioned by dt;
   Key run_id. Done when Copilot answers with code. Then step 5.
5. **Run it.** Goal: the code works in your notebook. Action: run what Copilot gives. Done
   when it runs. If the Toolbox refuses it, step 6.
6. **Fix a refusal.** Goal: code the Toolbox takes. Action: start a new chat with file 09,
   paste the code and the whole message, and ask for the fix. Done when Copilot answers
   with the fixed code. Then step 5.

## Decision rules

- If the Toolbox refused your code, load file 09.
- If your task is to convert an Excel workbook, attach files 15, 11 and 12 (or paste
  each as a message of its own), then attach the workbook and ask Copilot to convert
  it: a chat holds one file at a time, but for this one task.
- If you want a query of Hive someone else wrote as Toolbox code, load file 07. If you want
  their Hive made into Saved tables in your Project, end to end, load file 13. To carry
  tables from dev to prod once compared, load file 16.
- Otherwise, load the one file whose line under Which file names your task.
- If you want something else after a task, start a new chat with that task's file.

## Which file

# Copilot file 01: imports and the Project (sqlglot Composer 8.2)

**Follow these steps in order, as written: add no step, skip none, and reply as Output says.**

Objective: set up a Project, import what Toolbox code needs, and run a Statement.
Load this file when the user starts a Project, asks what to import, or asks how to run
something and see its rows.

## Terms

- **Toolbox**: sqlglot Composer 8.2, which writes Hive from Python.
- **Project**: a folder holding the Toolbox's folder, `sqlglot_composer/`, and the user's
  notebooks.
- **Statement**: one Hive query, built with `statement(...)`.
- **Table reference**: a file in references/ describing one table: its columns, types,
  partitions and Key, the columns that tell one row from another.
- **Saved table**: a table the user's own notebook writes.
- **Workflow**: a job's steps, run from its notebook in admin/workflows/.
- **Building block**: a piece of a Statement used in several notebooks.

## Always

1. Import each name you use, by name: `from sqlglot_composer import FROM, SELECT, statement`,
   never `import *`. Write only Toolbox names this file or the user's code shows. Hive's own
   words are Toolbox names only where this file writes them as functions, as SELECT and
   FROM: there is no COUNT, SUM, AND, CASE or ALIAS.
2. Build a Statement with `statement(...)`, its Clause functions in SQL order: a write's
   INSERT_OVERWRITE or INSERT_INTO first, then SELECT or SELECT_DISTINCT, FROM, the joins,
   WHERE, GROUP_BY, HAVING, ORDER_BY, LIMIT.
3. Name every calculation with AS: `AS(count_rows(), "runs")`; a plain column needs none.
   Arithmetic, `+ - * /`, works on Columns; write comparisons by rule 4.
4. Write each Condition with a function, in place of Python's ==, <, >, and, or, not on a
   Column: equals, not_equals, more_than, less_than, at_least, at_most, between, is_in,
   is_not_in, is_null, is_not_null, all_of, any_of. WHERE(a, b) keeps rows where both hold.
5. **Bound every read of a partitioned table** with a Condition giving a value for one of its
   partition columns, such as `equals(t.dt, "2026-09-24")`, `between(...)`, `is_in(...)` or
   `last_n_days(t.dt, 7)`: in WHERE for FROM, JOIN and CROSS_JOIN; inside ON= for LEFT_JOIN,
   SEMI_JOIN and ANTI_JOIN; for FULL_JOIN, in a Derived table it reads. Matching it to another
   table's column bounds nothing. A table with no partitions needs no bound.
6. Give every ORDER_BY a LIMIT.
7. Run a read with `run_query(s, query)` and a write with `run_execute(s, execute)`, after
   `from warehouse import query, execute`. Never call query or execute yourself.
8. Add an opt-out, such as `reads_all_partitions=True`, only when the user asks for what it
   allows, and say why in a comment.
9. Reach a column as `table.column`, from the user's Table reference:
   `from references.ops__job_runs import job_runs`, then `job_runs.dt`.
10. The user loads one Copilot file per chat, or for an Excel workbook files 15, 11 and
    12. If this one doesn't cover what is asked, say so and name the file that
    does, to load in a new chat: 01 imports and the Project, 02 Table references, 03
    building a Statement, 04 joins, 05 windows and subtotals, 06 saving a table, 07
    converting Hive, 08 checking and comparing, 09 fixing a refusal, 10 labels, Hive
    functions and Hive written by hand, 15, 11 and 12 an Excel workbook into Hive, 13 and 14 a
    whole job's steps from its Workflow notebook.

## A Project

- In a notebook in the Project's folder: `from sqlglot_composer import project`, then
  `project.start()`. It writes admin/, references/, building_blocks/, tables/ and
  warehouse.py.
- warehouse.py holds `conn`, the connection the user sets once, and two functions over it:
  `query(hive)` calls `conn.query`, running Hive that gives rows, and returns a pandas
  DataFrame; `execute(hive)` calls `conn.execute`, running Hive that changes something, and
  returns nothing. Nothing else in the Project reaches the warehouse.
- Each table read needs a Table reference: the references Workflow,
  admin/workflows/references/references.ipynb, runs
  `project.add_references(["ops.job_runs"], query=query)`, which writes
  references/ops__job_runs.py from the table's own description. The user fills in its `key=`.
- A Saved table: the new_table Workflow, admin/workflows/new_table/new_table.ipynb, runs
  `project.new_table("mart.job_day_runs")`, which writes its notebook and Table reference:
  file 06 says what goes in them.
- `project.check()` names each Workflow notebook's next step, `project.do_next()` runs those
  it can, and files 13, 14 and 16 list their steps.

## Imports, at the top of a cell, after the Toolbox's (rule 1)

- One table: `from references.ops__job_runs import job_runs`, then `job_runs.dt`.
- Every table of a database: `from references import ops`, then `ops.job_runs.dt`.
- The two calls: `from warehouse import query, execute`.
- A Building block: `from building_blocks.recent_runs import recent_runs`.
- A notebook in a subfolder, such as tables/mart__job_day_runs/, first puts the Project's
  folder on the path: `sys.path.insert(0, str(pathlib.Path.cwd().parents[1]))`, after
  `import pathlib` and `import sys`.

## Steps

1. **Read.** Goal: know the code's job. Action: list each table it reads, and whether it
   reads rows, writes or sets up the Project. Done when each table has its import; then step 2.
2. **Write.** Action: write one cell by this file. Done when every name in it is imported;
   then step 3.
3. **Check.** Action: run the Self-check; fix what fails, then reply.

## Decision rules

- If it reads rows: `rows = run_query(s, query)`, a DataFrame; never `query(s)` or
  `query(to_hive(s))`.
- If it sends a write, a CREATE TABLE or a SET line: `run_execute(s, execute)`.
- If the user wants only the Hive: `print(to_hive(s))`, which sends nothing, or
  `show_hive(s)`, laid out.
- If the user's code passes `send=`: write `query` or `execute`, which replaced it in 7.0.

## Output

Reply with these parts, in this order, and nothing else:

1. **Code**: one ```python block the user can paste into a notebook cell.
2. **Notes**: a few plain sentences: what it gives, each opt-out and why.

## Examples

Read the failed runs of one day, run it, and show the Hive:

```python
from sqlglot_composer import FROM, SELECT, WHERE, equals, run_query, statement, to_hive
from references.ops__job_runs import job_runs
from warehouse import query

s = statement(
    SELECT(job_runs.run_id, job_runs.job_id, job_runs.status),
    FROM(job_runs),
    WHERE(equals(job_runs.dt, "2026-09-24"), equals(job_runs.status, "FAILED")),
)
print(to_hive(s))
rows = run_query(s, query)
```

The same with `from references import ops`, where several tables are read:

```python
from sqlglot_composer import FROM, SELECT, WHERE, equals, statement
from references import ops

s = statement(
    SELECT(ops.job_runs.run_id, ops.job_runs.status),
    FROM(ops.job_runs),
    WHERE(equals(ops.job_runs.dt, "2026-09-24")),
)
```

- Every name used is imported by name and listed in a Copilot file's Names.

## Joins

- After FROM: `JOIN(other, ON=equals(other.job_id, t.job_id))`. ON= takes a Condition;
  several, with `all_of(...)`.
- Join on the joined table's whole Key. Joined on less, one row can match many, and the
  Toolbox warns that counts and sums may come out too big. Then join a Derived table with
  one row per value instead.
- The same table twice, or two tables of one name: give one a second name,
  `o = AS(other, "o")`, then use `o.job_id`.

## Partitions

- Each partitioned table needs its own bound, with a value; `equals(other.dt, t.dt)` matches
  rows but bounds nothing:
  - FROM and JOIN: in WHERE, `WHERE(equals(t.dt, day), equals(other.dt, day))`.
  - LEFT_JOIN, SEMI_JOIN and ANTI_JOIN: inside ON=,
    `ON=all_of(equals(other.job_id, t.job_id), equals(other.dt, day))`.
- A WHERE on a LEFT_JOIN's table is refused: it would throw away the rows with no match.
  Put that Condition in ON= instead.

## Decision rules

- If only rows with a match in both stay: JOIN.
- If every row of FROM's table stays, with NULL where `other` has no match: LEFT_JOIN.
- If every row of both stays: FULL_JOIN.
- If FROM's rows that have a match stay, each once, with no column of `other`: SEMI_JOIN.
- If FROM's rows that have no match stay: ANTI_JOIN.
- If the user asks for a right join: swap the tables and use LEFT_JOIN; there is no
  RIGHT_JOIN.
- If every row goes with every row: `CROSS_JOIN(other)`. A JOIN with no ON= is refused.
- If it counts matches after a LEFT_JOIN: `count_distinct(other.run_id)`, which gives 0 for
  a row with no match; `count_rows()` would give 1.
- If the user says the repeats are wanted: `many_matches=True`.
- If the user asks that a LEFT_JOIN keep only matched rows: `keeps_only_matches=True`, the
  opt-out that lets WHERE test its table.
- If the user asks Hive to copy a small table to every worker, to join it faster:
  `broadcast=True`, which is no opt-out.

## Formulas

- `+ - * /` as they are; `^` POWER; `&` CONCAT(a, b); TRUE, FALSE as they are.
- AND(a, b, c): `a AND b AND c`; OR(a, b): `(a OR b)`, bracketed, as AND joins before OR;
  NOT(x): `NOT x`. Hive has no AND() or OR() function: IF(AND(a, b), 1, 0) is
  IF(a AND b, 1, 0).
- IF as it is. IFS(c1, v1, c2, v2): `CASE WHEN c1 THEN v1 WHEN c2 THEN v2 END`.
  SWITCH(x, "a", 1, 0): `CASE x WHEN 'a' THEN 1 ELSE 0 END`.
- IFERROR(a / b, 0): COALESCE(a / b, 0), as a divide by 0 is NULL; IFNA(x, v) and
  XLOOKUP's fourth argument, v: COALESCE(x, v). ISBLANK(x): x IS NULL.
- ROUND, ABS, POWER, SQRT as they are; MOD(a, b): PMOD(a, b); INT: FLOOR; MIN(a, b) and
  MAX(a, b) of one row's cells: LEAST and GREATEST.

  one; WEEKDAY(d): DAYOFWEEK(d); TEXT(d, "yyyy-mm"): DATE_FORMAT(d, 'yyyy-MM').
- The first of d's month, DATE(YEAR(d), MONTH(d), 1) or EOMONTH(d, -1)+1:
  `CAST(TRUNC(d, 'MM') AS STRING)`. The Monday of d's week, d-WEEKDAY(d,2)+1:
  `CAST(NEXT_DAY(DATE_ADD(d, 7 * -1), 'MO') AS STRING)`.

- A summary's groups, written into the Hive (file 15): say so in the map, as a later day or
  team won't be in the table.
- SUMIFS(t[v], t[a], [@a], t[s], "x") over its own Table: `SUM(CASE WHEN s = 'x' THEN v
  END) OVER (PARTITION BY a)`. Over another Table: LEFT JOIN `(SELECT a, SUM(v) AS total
  FROM t WHERE s = 'x' GROUP BY a)`. Either way COALESCE(.., 0), as Excel gives 0 where
  nothing matches. COUNTIFS: COUNT(*), MAXIFS: MAX, MINIFS: MIN, each with COALESCE too;
  AVERAGEIFS: AVG, left NULL. SUMIF and AVERAGEIF(t[a], [@a], t[v]), COUNTIF(t[a], [@a]):
  the -IFS form, one match.
- RANK.EQ(x, t[x]) or RANK: `RANK() OVER (ORDER BY x DESC)`; with 1 as a third argument, ASC.

## Conditions in an -IF(S) form

- "x": `s = 'x'`; ">10", ">=", "<", "<=": that comparison; "<>x": `(s <> 'x' OR s IS NULL)`,
  as Excel counts a blank there; "<>" alone: `s IS NOT NULL`; ">="&[@d]: against this row's d.
- Every condition of one -IFS form holds at once: join them with AND, two on one column too
  (">10" and "<=30": `v > 10 AND v <= 30`). If two -IFS forms are added that differ in one
  value only, then that value is an OR: write one, with `s IN ('x', 'y')`.
- SUMPRODUCT over conditions: `*` between them is AND; `+` is OR where both can't hold at
  once, such as two values of one column, or written `((..)+(..)>0)`.
  SUMPRODUCT((t[s]="x")*(t[v]>5)*t[v]): `SUM(CASE WHEN s = 'x' AND v > 5 THEN v ELSE 0
  END)`; with no column to add, as `(..)*1`: `COUNT(CASE WHEN .. THEN 1 END)`. If it reads
  its own Table, then add OVER (), as each row shows the same total.
- A wildcard, "*ail*" or "f*": `LOWER(s) LIKE '%ail%'`, `'f%'`, as Excel ignores case.
- `t[d], "<="&[@d]` over its own Table is a running total, ties included as Excel's: `SUM(v)
  OVER (PARTITION BY a ORDER BY d RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`;
  COUNTIFS the same with COUNT(*). COUNTIFS(t[a], [@a], t[v], ">"&[@v])+1: `RANK() OVER
  (PARTITION BY a ORDER BY v DESC)`; with "<", ASC.

## Terms

- **Table**: an Excel Table; the workbook shows each as `Excel Table "name"`, its headers and

- **Typed column**: a column whose cells hold values; a **formula column** holds formulas.
- **Query**: a Power Query; the workbook lists each after its sheets as `Power Query "name"`,

## Decision rules

- If a Table has only typed columns and no query loads it, it is a source, never a final.
- If a Table has a formula column and no query loads it: if another Table's formula or a
  query reads it, it is a step; if nothing else reads it, it is a final. Its own formula
  columns reading its own row don't count.
- If a Table's only typed columns are the ones its SUMIFS or COUNTIFS match on, it is a

- If a Table has a Total Row, its Total Row is a final of its own, `<Table> (Total Row)`,

- Parameters and Keys are never a source, step or final.

- If the user asks for every step's cell, give each one as listed, in order.
- promote fills in a prod copy's location when it can: the one an earlier promote gave it,
  or the dev location with PROD in place of the Dev Database's name, as
  /data/team/mart_dev.db/x becomes /data/team/team_prod.db/x. Otherwise the location is a
  Decision left open, which `project.check()` names. Write each answer the user gives, or a
  location they want changed, in DECISIONS by the prod copy's name; if none is open, write
  `DECISIONS = {}`. A Decision is the user's, never yours.
- A prod copy is named for its dev table, in PROD. If the user wants another name, give
  `project.promote(TABLES, rename={"mart_dev.daily_fails": "fails"})`.

## Output

1. The Workflow and the user's step, in one line.
2. Each cell asked for in a ```python block, the names cell first.
3. Each Decision left to the user, then each later step, in words.

## How a Workflow runs

- DECISIONS holds each answer by the prod copy's name as `project.check()` writes it, each
  by its kind: `{"team_prod.daily_fails": {"location": "/data/team/team_prod.db/daily_fails"}}`;
  `project.write_decisions(DECISIONS)` writes each into its prod copy's Table reference.
- The last cell, `project.run_workflow(...)`, runs every step left, up to the first only the
  user can do; `dry_run=True` sends nothing.

## promote: dev tables to prod

Its input:

- TABLES: the dev tables to promote, by their full names, such as
  `["mart_dev.daily_job_runs"]`. Each prod copy reads the prod copies of the others
  promoted with it.

1. Promote each table: a prod copy of its folder and Table reference (it changes only files, so
   project.do_next() runs it for you).

       project.promote(TABLES)

2. Answer each prod table's open Decisions in the decisions cell (it is a decision, yours to
   make).
3. Write each answer into its prod table's Table reference (it changes only files, so
   project.do_next() runs it for you).

       project.write_decisions(DECISIONS)

4. Create each table in prod (it is a call to the warehouse, yours to run).

       for table in project.promoted_tables(TABLES):
           run_execute(project.load(table).create(), execute)

5. Seed each prod table that reads itself, once, from its original (it is a call to the
   warehouse, yours to run).

       to_seed = project.promoted_tables(TABLES, seeded=True)
       if not to_seed:
           print("Seeded nothing: no prod copy reads itself.")
       else:
           run_execute(hive_settings("dynamic_partitions"), execute)
           for table in to_seed:
               run_execute(project.load(table).seed(), execute)

6. Write each table in prod (it is a call to the warehouse, yours to run).

       project.run_tables(tables=project.promoted_tables(TABLES), execute=execute)

7. Refresh the Reference sheet and the Database modules (it changes only files, so
   project.do_next() runs it for you).

       project.refresh_reference_sheet(project.promoted_tables(TABLES))


## Example

The user: "mart_dev.daily_fails passed its compare. Promote it to prod: give the names cell
and step 1's cell." Its location is left for promote to fill in.

```python
TABLES = ["mart_dev.daily_fails"]

project.promote(TABLES)
```

## Self-check

- The reply names the Workflow and the user's step.
- Each cell is one listed here, with the user's names in it.
- Each table promoted has a compare that passed, or the reply says to run it first.
- Each later step is named in words, unless every cell was asked for.
- Each Decision answered is in DECISIONS by the prod copy's name; each other is named.
