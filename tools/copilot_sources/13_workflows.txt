## How a Workflow runs

Each Workflow has a notebook, admin/workflows/<name>/<name>.ipynb. The user fills in its
names cell, its inputs in capitals, such as NAME and TABLES, and its decisions cell,
DECISIONS, and saves it.
DECISIONS holds each answer by the table's name as project.check() writes it, each by its
kind: `{"mart_dev.weekly": {"location": "/data/team/mart_dev.db/weekly", "key": ["job_id"],
"types": {"fails": "bigint"}}}`; a later step, `project.write_decisions(DECISIONS)`,
writes each into its table's Table reference.
Each step's cell runs that step; the last cell, `project.run_workflow(...)`, runs every step
left, up to the first only the user can do, and `dry_run=True` sends nothing.
`project.check()` names the next step. A Decision is the user's: never answer it for them.
DEV and PROD, the Dev and Prod Databases, are set once in admin/databases.py.

## convert: someone else's Hive into Saved tables in dev

For any Hive, one query or many scripts. NAME is the batch's name (for the last cell alone,
a list of batches converted already). FILES are the .hql files, saved beside the notebook, in
admin/workflows/convert/, where it reads them; or FILES = [] and HIVE the Hive as text.
DATABASE is the database of a table the Hive names without one, such as "ops".
A staging table is one a statement of the Hive makes and a later one reads; convert's report
names each. Folded, its query goes inside each table that reads it, and it is never made;
kept, it becomes a Saved table of its own. STAGING is a dict, leaving the rest as convert
chooses (it folds one that is temporary or DROPped, and keeps any other):
{"ops_reports.failed": "fold"}, or "keep"; {} for none.

{workflow: convert}

## promote: dev tables to prod

TABLES are the dev tables, such as ["mart_dev.daily_job_runs"].

{workflow: promote}

## Worked example

```python

HIVE = None
```
