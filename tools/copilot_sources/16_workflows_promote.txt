# Copilot file 16: the promote Workflow, dev tables to prod ({version})

**Follow the steps below in order, as written. Add no step or call; reply as Output says.**

Objective: take the user through promoting tables from their Dev Database to their Prod
Database, with {version}, a Toolbox that writes Hive: the steps left, each its cell of the
promote Workflow's notebook, in order. Load this file when the user asks how to carry dev
tables to prod. File 13 is for converting Hive into dev first; file 14 for new tables, Table
references, upgrades and changes to a Saved table; a step's own file, for the Python inside
it.

## Terms

- **Workflow**: ordered steps to one end goal; each step is a cell of its notebook,
  admin/workflows/<name>/<name>.ipynb. Its **names cell** holds its inputs in capitals.
- **Decision**: one thing about one table only the user decides, such as its location, Key
  or a column type, answered in the **decisions cell**, DECISIONS.
- **Saved table**: a table the user's own code writes; its **Table reference** is the file
  of its columns, partitions, Key and location.
- **DEV**, **PROD**: the Dev Database, where tables are built and compared, and the Prod
  Database, where others read them; set once in admin/databases.py.
- **prod copy**: the Saved table promote makes in PROD from a dev table: its own Table folder
  and Table reference, named for the dev table with PROD for its database.
- **query**, **execute**: the user's warehouse calls, from warehouse.py; a Workflow
  notebook's first cell imports them with the Toolbox's names.

## Decision rules

- **Promote a table only once its compare has passed** in the convert Workflow, or it is
  written by the new_table Workflow (file 14). If the user hasn't said so, say so before any
  cell.
- If the user asks for particular cells, give those: a step's cell runs only once the steps
  before it are done.
- If the user asks for every step's cell, give each one as listed, in order.
- promote fills in a prod copy's location when it can: the one an earlier promote gave it,
  or the dev location with PROD in place of the Dev Database's name, as
  /data/team/mart_dev.db/x becomes /data/team/team_prod.db/x. Otherwise the location is a
  Decision left open, which `project.check()` names. Write each answer the user gives, or a
  location they want changed, in DECISIONS by the prod copy's name; if none is open, write
  `DECISIONS = {}`. A Decision is the user's, never yours.
- A prod copy is named for its dev table, in PROD. If the user wants another name, give
  `project.promote(TABLES, rename={"mart_dev.daily_fails": "fails"})`.

## How a Workflow runs

- DECISIONS holds each answer by the prod copy's name as `project.check()` writes it, each
  by its kind: `{"team_prod.daily_fails": {"location": "/data/team/team_prod.db/daily_fails"}}`;
  the next step writes each into its prod copy's Table reference.
- The last cell, `project.run_workflow(...)`, runs every step left, up to the first only the
  user can do; `dry_run=True` sends nothing.

## promote: dev tables to prod

Its input:

- TABLES: the dev tables to promote, by their full names, such as
  `["mart_dev.daily_job_runs"]`. Each prod copy reads the prod copies of the others
  promoted with it.

{workflow: promote}

## Example

The user: "mart_dev.daily_fails passed its compare. Promote it to prod: give the names cell
and step 1's cell." Its location is left for promote to fill in.

```python
TABLES = ["mart_dev.daily_fails"]

project.promote(TABLES)
```
