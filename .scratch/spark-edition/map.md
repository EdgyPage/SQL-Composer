# SQL Composer: the PySpark edition

Label: wayfinder:map

## Destination

Two Editions of the Toolbox, built and exported together as 3.0. `sql_composer/` writes its Hive
through sqlglot. `spark_composer/` ("Spark Composer") writes the same Hive with its own printer
and runs it on Spark. They share every Guard, Load limit, Table reference rule, lineage page,
Worked example and test that doesn't depend on the library, and they can't drift apart without
a test failing. `main` holds both folders and one README; the user copies whichever folder work
uses.

## Notes

- **Execution override: ON.** As on the v2 map, the user chose built Editions over a spec. Each
  ticket below is a build step, and each keeps the suite green.
- **Why two Editions.** The user hasn't settled which engine work will use, so both are to be
  fully built: code, tests, Worked examples, gallery, lineage, docs and admin.
- **The user's decisions (2026-09-29), which every ticket holds to:**
  - The PySpark edition is the package `spark_composer`, product "Spark Composer", beside
    `sql_composer` so both can sit side by side at work.
  - It imports only the standard library, pandas, numpy and pyspark. There is no sqlglot in it.
    It prints its SQL text itself and runs it with `spark.sql()` on Spark with Hive support,
    over the same partitioned Hive tables.
  - Both Editions have the same 63 public names, `to_hive` and `hive_function` included, and
    the same `run(s, send=...)`. At work a Spark user writes
    `send=lambda hive: spark.sql(hive).toPandas()`.
  - One Clean branch, `main`, holds `sql_composer/`, `spark_composer/` and one
    `.github/README.md`.
  - One TOOLBOX_VERSION for both Editions, held equal by a test, raised to 3.0 when the PySpark
    edition ships, with one change history.
  - pyspark `>=3.5.0,<4.1` (the pandas 2.0.3 pin rules out 4.1 and newer). `dev` pins 4.0.4, and
    CI runs 3.5.0 and 4.0.4 on JDK 17.
  - The user installs JDK 17 on their Windows 11 machine themselves. Writes to real tables are
    tested only on Linux CI (Windows would need winutils).
  - For 3.0, SQL Composer's own Hive changes so both Editions write the same text: week_start and
    month_start are wrapped in `CAST(... AS STRING)`; Spark's reserved words get backticks;
    create_table takes only types on an explicit Hive list. A value holding BEL, FF or VT is
    refused, and that fix ships early, as a 2.1 bug fix.
  - `hive_function` checks its arguments and its aggregate flag against one shared list in both
    Editions, and a call is compared and shown as written.
  - At work, the notebook kernel runs pyspark itself.
- **Defaults Claude chose, which the user approved with the plan:** only the PySpark edition writes
  `a / NULLIF(b, 0)` when dividing by a column (Spark 4 raises on divide-by-zero with ANSI on);
  `import spark_composer` stops without pyspark, as `sql_composer` stops without sqlglot; CI tests
  pyspark at exactly 3.5.0 unless the spike shows it unusable; `main` may be re-exported as 2.1
  while the Hive stays byte-identical; claims in shared docstrings and refusal reasons that hold
  only on Hive are reworded to hold on both engines.
- **The shape.** A Statement is already plain Python; sqlglot sits only at its leaves, in the
  writer, in the Example database's executor and in the import self-check. So the split is:
  - a Toolbox-owned expression tree (`trees.py`) in place of sqlglot's at the leaves;
  - two files per Edition with the same names and interface: `writing.py` (sqlglot, or the
    hand printer) and `engine.py` (the library check and the Example database's runner);
  - every other file shared. `sql_composer/` is the hand-edited source, and `spark_composer/`
    holds copies generated by `tools/make_spark_edition.py`, with the package and product names
    swapped, committed and staleness-tested like `examples.html`.
- **Byte-identity.** SQL Composer's Hive, public names and messages stay byte-identical until
  ticket 25, held by the golden corpus (ticket 3), `examples.html` and the existing exact-text
  tests. Only ticket 25 changes the Hive, and only as the user approved.
- **Import tiers.** Shared files import only the standard library, pandas and numpy. Spark's
  `writing.py` imports only the standard library and its own package. Each `engine.py` may also
  import its own library. Only SQL Composer's `writing.py` and `engine.py` import sqlglot.
- **Declared differences.** Every place the two Editions' Hive differs is one row of
  `DECLARED_DIFFERENCES` in `tools/editions.py`, with its reason. After 3.0 there should be two:
  division by a column, and `hive_function` written as given.
- **The Example database of the PySpark edition** runs Spark in a private helper process, so it
  can never touch the user's own session or warehouse.
- **Tests.** One suite. `python -m pytest` runs the sqlglot edition and the repo tests;
  `python -m pytest --edition spark` runs the same tests against `spark_composer`.
- **Still true from the v2 map:** beginner readability is the governing test, now in both
  Editions; there is no probing at work; everything the Toolbox produces is generated; only the
  user raises the version and pushes `main`. The v2 map's Notes hold for both Editions unless
  marked "Changed by the PySpark edition".
- **Skills.** Research tickets call `research`, the spike calls `prototype`, and task tickets
  are built test-first with `tdd` and finished by the Definition of done in `CLAUDE.md`.

## Not yet specified

- **Whether the tables at work are Hive ACID (transactional).** Spark can't read or write those
  correctly without the Hive Warehouse Connector. The README tells a Spark user to check before
  writing a Saved table.
- **The Spark settings at work** that decide how the text reads: `spark.sql.ansi.enabled`,
  `spark.sql.parser.escapedStringLiterals` and `spark.sql.ansi.enforceReservedKeywords`. The
  README names them for a one-time check by hand.
- **Whether Hive at work is 2.2 or newer.** If so, `NULLIF` can move into both Editions and the
  division row goes.
- **Lineage for SQL the Toolbox didn't build** (still unspecified on the v2 map). It can only
  ever exist in the sqlglot edition.

## Out of scope

- **The DataFrame API.** The PySpark edition writes Hive text; it never builds DataFrames.
- **Vendoring sqlglot** into the PySpark edition.
- **Dialects other than Hive**, as on the v2 map.
- **Writes to real tables on Windows.** They are tested on Linux CI only.
