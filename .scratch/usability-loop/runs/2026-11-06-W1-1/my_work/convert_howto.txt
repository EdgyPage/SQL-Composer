9. Convert someone else's Hive Getting started
Goal
Turn scripts of Hive someone else wrote, with their temporary tables, their FROMs with several INSERTs, their incremental INSERTs and their Script tags, into your own code. Hive is the SQL your warehouse runs. You end with a Saved table, a real table your own Statements write, in your Dev Database for each table the scripts write; your Dev Database is the database where you may create and write tables of your own. Each Saved table's notebook builds the same query from the Toolbox's functions, is compared with the table it copies, its original, and is then promoted to your Prod Database, the database others read your finished tables from. That is a Conversion, and the convert Workflow, an ordered list of steps in a notebook of its own, takes you through it, step by step. What no Toolbox function writes yet stays Hive, at the smallest size it can, so you get the rest converted rather than none of it.
When you'd use it
If you inherit Hive that works but that you can't maintain, such as a nightly job another team wrote or a folder of scripts that has grown for years, convert it as the steps below do. Converted, the Guards check it, Lineage traces it, and you change it in one place, dev, before promoting it.If one script writes a table another reads, convert both in one batch, as step 3 does.If a Script tag stands for a day that changes each run, such as the latest day a table holds, answer it with a Run value, the value a function of yours gives at each write, as step 8 does.If a table that reads itself has years of rows you don't need, limit its seed, the one copy of the original's rows, by Partition, as step 6 does.If several tables share an answer, such as accepting each one's proposed Key, give it once under "all_tables", as step 6 does.If the scripts are simple and read none of each other's tables, convert each as a batch of its own, as One batch per script, below, says.If your Database settings aren't filled in yet, do Set your Database settings first: each table is placed under DEV's "location_root", so its folder is no Decision.If you have no Project yet, do Start a Project first.If you have not yet written a Saved table of your own, read Save a table first.

2. Save the scripts
Goal: the scripts where the convert Workflow reads them. Save each script as it is, a .hql file beside the convert Workflow's notebook, in admin/workflows/convert/. Each is read where it is, never copied; a script kept somewhere else is named in FILES by its path, such as "C:/work/daily.hql". Here the ops team's two: the nightly one keeps the day's failed runs in a temporary table, then counts the day's alerts two ways from one FROM; the weekly one adds each failed job to a history the job reads itself. The nightly one holds a Script tag, <PARM="RUN_DAY"/>: the scheduler that runs the script puts the day in its place before Hive reads it. Its author tagged only that one day; the others are typed in, and the converted code keeps them as they are:
The file admin/workflows/convert/daily.hql, after you save it
[PRE]
SET hive.exec.parallel=true;
DROP TABLE IF EXISTS ops_reports.failed_runs;
CREATE TEMPORARY TABLE ops_reports.failed_runs AS
SELECT r.run_id, r.job_id, r.dt
FROM ops.job_runs r
WHERE r.dt = '2026-09-24' AND r.status = 'FAILED';
FROM ops.run_alerts a
INSERT OVERWRITE TABLE ops_reports.alerts_by_severity PARTITION (dt='2026-09-24')
  SELECT a.severity, COUNT(*) AS alerts WHERE a.dt = <PARM="RUN_DAY"/> GROUP BY a.severity
INSERT OVERWRITE TABLE ops_reports.alerted_runs PARTITION (dt='2026-09-24')
  SELECT a.run_id, COUNT(*) AS alerts WHERE a.dt = '2026-09-24' GROUP BY a.run_id;

CREATE TABLE IF NOT EXISTS ops_reports.fail_history (job_id BIGINT, fails BIGINT)
PARTITIONED BY (dt STRING) STORED AS ORC;

4. Read what each statement became
Goal: know what the Conversion made of each statement. The scripts' order doesn't matter: the batch orders each statement by what reads what. Each table the scripts write is a Saved table in mart, with its Table folder, the folder that holds everything about one Saved table, its Table reference, the file that describes the table's columns, Partitions and Key, and its Decisions to answer. Its location=, the folder its files go in, is placed under DEV's "location_root", as /data/dev/mart.db/fail_history, so it is no Decision. The one exception is the temporary table: a Staging table, a table a script writes only so a statement after it can read it. The weekly script reads it, so it is folded into fail_history, its query a Derived table there, a named query that lives only inside the Statement that reads it, and never made a table of its own. To keep it a table instead, give staging={"ops_reports.failed_runs": "keep"}. The FROM with two INSERTs gives each target a Saved table of its own. The DROP becomes nothing, and the SET line becomes the Session settings of the writes after it: a Session setting is a Hive SET sent before a Statement. The Script tag is read past, as if a day stood there: alerts_by_severity's WHERE becomes WHERE(equals(a.dt, script_tag(TAGS["RUN_DAY"]))), and TAGS, in its Table reference, says <PARM="RUN_DAY"/> until you answer it. admin/workflows/convert/ops_reports/batch.md names where each script is, read where it is, and lists what each statement became:

Each answer, by its kind:
"all_tables" answers for every table of the batch at once, and a table's own answer overwrites it. Its "key": "proposed" accepts each table's proposed Key, as if you typed it: a Key project.convert could work out of a table's query, as GROUP BY a.severity gives one, is proposed in its Table reference already, marked # proposed, and is kept even unanswered, since the query proves it. So "key": "proposed" isn't needed here, but it does no harm: for a Key kept already it only takes off the # proposed mark, and you needn't tell the two kinds of Key apart. The other kind is the references Workflow's: a Key add_references proposes from a table's rows stays open, key=None, # TODO: proposed [...], until you accept it. Here it is kept, the day as text. A Partition is a slice of a table: the rows that share one value of each column it is partitioned by."tags": the Script tag's answer is the Hive the scheduler put in its place. With no "seed", it copies every Partition the original holds, years of them perhaps; here it copies only those from 2026-09-01 on.
