6. Save a table Getting started

Goal

Keep a Statement's rows in a Saved table: a real table in the warehouse that your Project writes, and that other Statements then read like any other table. A Statement is one query; a Project is your folder of scripts at work, in the Toolbox's fixed layout. project.new_table makes the table's Table folder, the folder that holds everything about one Saved table, with a Table notebook in it, the notebook whose cells create and write the table, made from the saved_table Template, the empty shape of such a notebook. It also makes the table's Table reference, the file that describes the table's columns. You fill in both, try the notebook's steps, and from then on project.run_tables writes the table with the Project's other Saved tables.

When you'd use it

If a result is slow to work out, save it in a Saved table: working it out once is cheaper than working it out again every time someone asks.

If many notebooks and dashboards read a result, save it in a Saved table, so each reads the rows already worked out.

If you need each Partition's rows kept as they were when they were written, save them in a Saved table. A Partition is a slice of a table: the rows that share one value of each column the table is partitioned by, such as one day.

If you only need the rows once, run the Statement with run_query instead, as Build and run a first statement shows.

The Example database, the small made-up tables this page runs on, can be read but not written to. So on this page each write shows its Hive, ready to paste, and a write that is sent goes to warehouse.py's execute, which here calls example_database.execute: it prints the write's first line and changes nothing. At work, the same calls send it to your warehouse, through your own execute.

__all__ = ["job_runs", "jobs", "run_alerts"]
_TABLES = __all__

def __getattr__(name: str) -> NoReturn:
    """A name that isn't one of its tables: say which tables it has, and the closest."""
    if name.startswith("_"):
        raise AttributeError(name)
    close = difflib.get_close_matches(name, _TABLES, n=1)
    hint = f" Did you mean {close[0]!r}?" if close else ""
    raise AttributeError(f"ops has no table {name!r}.{hint} Its tables are: "
                         f"{', '.join(_TABLES)}.", obj=None)

def __dir__() -> list[str]:
    """Its tables, so tab completion lists them."""
    return list(_TABLES)

    of the rows READS picks.

    A partitioned table's partition columns come last in SELECT, in its Table reference's

    values, and replaces only the Partitions they fill. They stay in GROUP_BY too, so each
    Partition's rows stay apart.

        SELECT(
            <SOURCE_TABLE>.<GROUP_COLUMN>,  # what each row is for
            AS(count_rows(), <COUNT_NAME>),
            <SOURCE_TABLE>.<PARTITION_COLUMN>,  # this table's partition column, last

        FROM(<SOURCE_TABLE>),
        WHERE(READS),
        GROUP_BY(
            <SOURCE_TABLE>.<GROUP_COLUMN>,
            <SOURCE_TABLE>.<PARTITION_COLUMN>,  # kept, so each Partition's rows stay apart

    ]

    """Step 1: create mart.alerts_per_severity from its Table reference, if it isn't there yet."""
    return create_table(alerts_per_severity, may_exist=True)

def rows() -> list[Clause]:
    """The clauses preview and write share, so the two can never disagree: a count per group
    of the rows READS picks.

    A partitioned table's partition columns come last in SELECT, in its Table reference's
    order, named as it names them: INSERT_OVERWRITE fills each Partition from the rows' own
    values, and replaces only the Partitions they fill. They stay in GROUP_BY too, so each
    Partition's rows stay apart.
    """
    return [
        SELECT(
            run_alerts.severity,  # what each row is for
            AS(count_rows(), "alerts"),
            run_alerts.dt,  # this table's partition column, last
        ),
        FROM(run_alerts),
        WHERE(READS),
        GROUP_BY(
            run_alerts.severity,
            run_alerts.dt,  # kept, so each Partition's rows stay apart
        ),
    ]

def preview() -> Statement:
    """Step 2: the rows write() would save, as a SELECT to run and check first."""
    return statement(*rows())

def write() -> Statement:
    """Step 3: save the rows, replacing the Partitions they fill, or the whole table if it
    isn't partitioned: sent twice, it leaves the same rows, not twice as many."""
    return statement(INSERT_OVERWRITE(alerts_per_severity), *rows())

10. Choose how a write fills its Partitions

Goal: know which of the two ways a write fills Partitions you want.

The Template's write selects the partition column, run_alerts.dt, and its Hive says PARTITION(dt) with no value: each row goes to the Partition its own dt names, so a write whose READS picks several days fills each of them. Common mistakes

Selecting the partition column a write names

With partition={"dt": ...}, the day comes from partition=, so a write that also selects run_alerts.dt is refused as you build it:

statement(
    INSERT_OVERWRITE(alerts_per_severity, partition={"dt": "2026-09-24"}),
    SELECT(run_alerts.severity, AS(count_rows(), "alerts"), run_alerts.dt),
    FROM(run_alerts),
    WHERE(equals(run_alerts.dt, "2026-09-24")),
    GROUP_BY(run_alerts.severity, run_alerts.dt),
)

Python stops with this message

GuardRefused:
  What happened:  INSERT_OVERWRITE(alerts_per_severity): it also selects dt.
  Why it matters: The warehouse fills a table's columns by position, not by name, so a missing or extra column would put values in the wrong columns.
  Usual fix:      SELECT every column of alerts_per_severity's Table reference, each under its own name, except a partition column the write names in partition={...}. The Toolbox puts them in the right order, its partition columns last.
  Opt-out:        none - this one can't be switched off.

Pick one of the two ways: select only run_alerts.severity and the count with partition=, or leave partition= out and let the rows fill it, as the Template does.

Leaving the partition column out of GROUP_BY

Each row of the result is one group, so a column in SELECT must be in GROUP_BY. The Template keeps the partition column in both: dropped from GROUP_BY, the write is refused by a Guard, a check that refuses a Statement that would give a wrong result:

statement(
    INSERT_OVERWRITE(alerts_per_severity),
    SELECT(run_alerts.severity, AS(count_rows(), "alerts"), run_alerts.dt),
    FROM(run_alerts),
    WHERE(equals(run_alerts.dt, "2026-09-24")),
    GROUP_BY(run_alerts.severity),
)

Python stops with this message

GuardRefused:
  What happened:  SELECT has run_alerts.dt, which GROUP_BY leaves out.
  Why it matters: Each output row is one group, so a column that isn't grouped has no single value to show. Hive would refuse the Statement.
  Usual fix:      Add run_alerts.dt to GROUP_BY. To keep one whole row per group instead, such as each job's latest run, number the rows with row_number(...) inside derived(...), then keep number 1 with WHERE(equals(..., 1)); help(row_number) shows how.
  Opt-out:        none - this one can't be switched off.

Keep the partition column in GROUP_BY as well as in SELECT: GROUP_BY(run_alerts.severity, run_alerts.dt), as the Template's rows() does.
