
9. Convert someone else's Hive Getting started

Goal

Turn scripts of Hive someone else wrote, with their temporary tables, their FROMs with several INSERTs and their incremental INSERTs, into your own code. Hive is the SQL your warehouse runs. You end with a Saved table, a real table your own Statements write, in your Dev Database for each table the scripts write; your Dev Database is the database where you may create and write tables of your own. Each Saved table's notebook builds the same query from the Toolbox's functions, is compared with the table it copies, its original, and is then promoted to your Prod Database, the database others read your finished tables from. That is a Conversion, and the convert Workflow, an ordered list of steps in a notebook of its own, takes you through it, step by step. What no Toolbox function writes yet stays Hive, at the smallest size it can, so you get the rest converted rather than none of it.

When you'd use it

If you inherit Hive that works but that you can't maintain, such as a nightly job another team wrote or a folder of scripts that has grown for years, convert it as the steps below do. Converted, the Guards check it, Lineage traces it, and you change it in one place, dev, before promoting it.
If one script writes a table another reads, convert both in one batch, as step 3 does.
If you have no Project yet, do Start a Project first.
If you have not yet written a Saved table of your own, read Save a table first.

2. Save the scripts

Goal: the scripts where the convert Workflow reads them. Save each script as it is, a .hql file beside the convert Workflow's notebook, in admin/workflows/convert/. Here the ops team's two: the nightly one keeps the day's failed runs in a temporary table, then counts the day's alerts two ways from one FROM; the weekly one adds each failed job to a history the job reads itself:

The file admin/workflows/convert/daily.hql, after you save it

SET hive.exec.parallel=true;
DROP TABLE IF EXISTS ops_reports.failed_runs;
CREATE TEMPORARY TABLE ops_reports.failed_runs AS
SELECT r.run_id, r.job_id, r.dt
FROM ops.job_runs r
WHERE r.dt = '2026-09-24' AND r.status = 'FAILED';
FROM ops.run_alerts a
INSERT OVERWRITE TABLE ops_reports.alerts_by_severity PARTITION (dt='2026-09-24')
  SELECT a.severity, COUNT(*) AS alerts WHERE a.dt = '2026-09-24' GROUP BY a.severity
INSERT OVERWRITE TABLE ops_reports.alerted_runs PARTITION (dt='2026-09-24')
  SELECT a.run_id, COUNT(*) AS alerts WHERE a.dt = '2026-09-24' GROUP BY a.run_id;

The file admin/workflows/convert/weekly.hql, after you save it

CREATE TABLE IF NOT EXISTS ops_reports.fail_history (job_id BIGINT, fails BIGINT)
PARTITIONED BY (dt STRING) STORED AS ORC;
INSERT INTO TABLE ops_reports.fail_history PARTITION (dt='2026-09-24')
SELECT f.job_id, COUNT(*) AS fails
FROM ops_reports.failed_runs f
WHERE f.job_id NOT IN (SELECT h.job_id FROM ops_reports.fail_history h WHERE h.dt = '2026-09-24')
GROUP BY f.job_id;

4. Read what each statement became

Goal: know what the Conversion made of each statement. The scripts' order doesn't matter: the batch orders each statement by what reads what. Each table the scripts write is a Saved table in mart, with its Table folder, the folder that holds everything about one Saved table, its Table reference, the file that describes the table's columns, Partitions and Key, and its Decisions to answer. The one exception is the temporary table: a Staging table, a table a script writes only so a statement after it can read it. The weekly script reads it, so it is folded into fail_history, its query a Derived table there, a named query that lives only inside the Statement that reads it, and never made a table of its own. To keep it a table instead, give staging={"ops_reports.failed_runs": "keep"}. The FROM with two INSERTs gives each target a Saved table of its own. The DROP becomes nothing, and the SET line becomes the Session settings of the writes after it: a Session setting is a Hive SET sent before a Statement. admin/workflows/convert/ops_reports/batch.md lists what each statement became:

print(Path("admin/workflows/convert/ops_reports/batch.md").read_text(encoding="utf-8"))

6. Answer each Decision in the decisions cell

Goal: an answer for each open Decision. Write each answer in the convert Workflow notebook's decisions cell, DECISIONS, by each table's name as project.check() writes it. A TODO line left, such as does_not_add_up=, waits on nothing. This page stands in for the decisions cell:

Common mistakes

Converting one script at a time

A table one script writes and another reads is made once, and read in dev, only when both are in one batch. Give the scripts together, with files=.

Leaving a Decision open

The Workflow waits on each table's open Decisions, each one only you can make, such as a table's folder. Answer each one project.check() names in the decisions cell.

Promoting before comparing

promote refuses a table whose compare hasn't passed, so prod never gets rows that differ from the original's. Compare each table, and fix it in dev until its compare passes, then promote.
