Every Workflow

A Workflow is a notebook in admin/workflows/ whose steps take you from what you start with to one end goal. Click a box for its steps.

Which one

  • references: Table references from DESCRIBE.
  • the Excel path: a workbook, in code or by Copilot.
  • new_table: a new Saved table, in dev.
  • convert: someone else's Hive, into dev.
  • promote: dev tables carried to prod.
  • schedule: a run for your scheduler.
  • change_a_saved_table: a change sent to one table.
  • upgrade: after a new Toolbox comes.

How its notebook runs

The convert, promote, new_table and references notebooks read top to bottom, in four cells:

  1. Name what it works on: fill in the names cell, the code cell under the setup cell, and save the notebook.
  2. Run up to your Decisions: run the cell under it; it runs every step up to the first only you can do, and prints the DECISIONS to paste.
  3. Make the decisions: paste it over the decisions cell, fill it in, and save.
  4. Run the rest: run the cell under the decisions cell; it goes on from where it stopped.

In upgrade, change_a_saved_table and schedule, run each step's cell in turn.

Each step's tag says what it is: files only changes only files, or only prints; calls the warehouse sends to the warehouse, when you run it; your decision waits on you.

Words

  • Saved table: a real table in the warehouse that your code writes.
  • Table reference: a file describing one table: its columns, Partitions and Key.
  • Decision: one thing about one table that only you decide, such as its Key.
  • Key: the columns whose values name exactly one row.
  • Partition: a slice of a table, such as one day's rows.
  • Dev and Prod Database: where your tables are built and checked first, and where others read them once promoted.

Beside the Workflows

Of the notebooks in admin/ that belong to no one Workflow, two watch the Project as a whole: admin/check_project.ipynb, which checks the Project and names the next step of each Workflow you have started, and admin/lineage.ipynb, which records the Lineage state and exports the Lineage difference: what changed a column, and where up its chain.

Common tripping points

  • Run a notebook's cells one at a time, never Run All: a step after a decision would write before you make it.
  • Fill in connect(...) in each notebook's setup cell, its first code cell: until you do, query and execute refuse.
  • "Run up to your Decisions" runs to the end when nothing waits on you, writing and comparing each table: to see what it would send first, add dry_run=True to its project.run_workflow(...) call.
  • Paste what it prints over the decisions cell, fill in each "<FILL IN>" and save the notebook before you run on.
  • Lost your place? project.check() names the next step of each Workflow you have started.
  • In a script of your own, not a notebook, print a Project action's report, such as print(project.check()): a script shows nothing on its own.
  • Edited a logic cell, a Table reference or a Building block yourself? Run project.record_lineage_state() in admin/lineage.ipynb, or any Table notebook's cell 5, which records the whole Project: until you do, project.check() says the Lineage state is behind.

references

Writes a Table reference for each table your Project reads, from its DESCRIBE.

Its notebook: admin/workflows/references/references.ipynb. Its names cell: TABLES.

Starts from

  • table names your query can DESCRIBE

Ends with

  • filled-in Table references
  • the Reference sheet
  • the Database modules

Its steps

  1. Write the Table references from DESCRIBEcalls the warehouse
  2. Answer each table's open Decisions in the decisions cellyour decision
  3. Write each answer into its table's Table referencefiles only
  4. Refresh the Reference sheet and the Database modulesfiles only

Common tripping points

  • Run it before convert or new_table: the tables they read need their Table references first.
  • A Key is the columns whose values name exactly one row: check yours with check_key before you answer it, giving a partitioned table where=, one Partition.

Hand-offs

  • On to new_table: a Table reference for each table its logic reads.
  • On to convert: a Table reference for each table its scripts read.

the Excel path

Turns a Formula workbook into Saved tables through the convert Workflow, which reads the workbook itself, or the Hive Copilot writes from it, then on to prod through promote.

Its steps

  1. Take your workbook as it is
  2. Save it in admin/workflows/convert/, beside the convert notebook, and give it to convert in FILES
  3. Or give Copilot files 15, 11 and 12 with the workbook's text, and 23 for a total, 20 for a PivotTable and 24 for its filter, as copilot/00_start_here.txt's Index says
  4. Read the Workbook check, in convert's report and the batch's batch.md
  5. Answer each table's Decisions, a PivotTable's name, the warehouse table each Table stands for, proposed from its name, and each Pivot filter among them, then create and write each in dev, as the Workflow's steps say
  6. Compare each with its query, the Hive it was converted from
  7. Promote them, and create and write each in prod, through the promote Workflow

Common tripping points

  • Name the workbook in FILES, such as FILES = ["costs.xlsx"]: FILES left [] reads only the .hql files beside the notebook.
  • Read the Workbook check at the end of convert's report: it runs each table's Hive over the workbook's own Tables, never the warehouse, and lists each cell that differs.
  • A PivotTable's slicer or filter is a Decision: "keep" keeps its selection; to tab through each value later, as with the slicer, "fold" keeps every value in one table.
  • Give Copilot files 15, 11 and 12 from the copilot/ folder with the workbook, and 23 for a total, 20 for a PivotTable and 24 for its filter, as 00_start_here.txt's Index says; to grow a converted PivotTable later, file 21 with 03, 05 and 06, and file 22 with 06 and 17 for its Pivot filters at scale.
  • A Table needn't be named as the warehouse names its table: the table each Table stands for is a Decision, proposed from its name, Table1 as ops.table1; answer "sources" with the table its rows came from, in any database.
  • A PivotTable becomes one table of its rows, each Row and Column field a column: its Grand Totals and subtotals are left out, each named in the table's checklist.
  • Check each name Copilot leaves in angle brackets, such as <database>, against your sheet's notes before you fill it in.
  • A Table's Total Row, its sums under its last row, becomes a query of its own: a Saved table refuses subtotal rows.
  • A list typed into the workbook, such as its teams, and each value on its Parameters sheet are written into the Hive as they are: a team added later, or a changed rate, doesn't reach the table until you change the Hive.

Hand-offs

  • On to convert: the workbook itself, or its Hive from Copilot saved as .hql files beside it, as one batch.

new_table

Makes a Table folder for each new Saved table: from its query, when QUERIES gives one, its logic written for you; else from a Template, its logic for you to write. A Building block, a piece several notebooks share, is made with project.new_block(...).

Its notebook: admin/workflows/new_table/new_table.ipynb. Its names cell: TABLES, QUERIES.

Starts from

  • the tables' names
  • what each table should hold

Ends with

  • a dev Table folder whose logic loads
  • written in dev
  • its Table reference
  • each from a query compared with it

Its steps

  1. Make each Table folder, converting each table's query QUERIES givesfiles only
  2. Write each table's logic in its Table notebook, and save ityour decision
  3. Write each Table reference from its logicfiles only
  4. Answer each table's open Decisions in the decisions cellyour decision
  5. Write each answer into its table's Table referencefiles only
  6. Check each table's rows with preview(), which writes nothingcalls the warehouse
  7. Create and write each in devcalls the warehouse
  8. Compare each table made from a query with its querycalls the warehouse

Common tripping points

  • The tables its logic reads need their Table references first: run references for them.
  • Have a query already? Give it in QUERIES, and its logic is written for you, by a convert batch run for you; else you write the logic in its Table notebook, where step 2 waits on you.
  • Step 2 waits on you even with no Decision open: its cell's preview() says what stops a table's logic, if anything does. Mend it, save the Table notebook, and run "Run up to your Decisions" again: it goes on from step 2.
  • A Table notebook's TODO lines are yours: fill each in, or delete it.

Hand-offs

  • From references: a Table reference for each table its logic reads.
  • On to promote: tables in dev, each Decision made.

convert

Turns Hive someone else wrote, one query or a batch of scripts, into your own code: each table the scripts write becomes a Saved table in your Dev Database, with its Table folder, and what only you can decide of it, a Decision, answered in the decisions cell.

Its notebook: admin/workflows/convert/convert.ipynb. Its names cell: NAME, FILES, HIVE, EACH_SCRIPT_ITS_OWN_BATCH, DATABASE, RENAME, STAGING, PARTITIONS.

Starts from

  • Hive scripts
  • your Dev Database's name
  • read access to the sources

Ends with

  • a dev Table folder per table the scripts write
  • each written in dev
  • each compared with its original
  • each answer written in

Its steps

  1. Convert the scripts: each table they write a Saved table in devcalls the warehouse
  2. Answer each table's open Decisions in the decisions cellyour decision
  3. Write each answer into its table's Table referencefiles only
  4. Create each table in devcalls the warehouse
  5. Seed each table that reads itself, once, from its originalcalls the warehouse
  6. Write each table in devcalls the warehouse
  7. Compare each table with its originalcalls the warehouse

Common tripping points

  • The tables its scripts read need their Table references first: run references for them.
  • A table's copy in dev is named for the table and its database: mart.team_fails becomes mart_dev.team_fails_mart. Give RENAME in the names cell for a name of your own.
  • One query, not a whole script? convert takes it, or new_table's QUERIES, which runs a convert batch for you.
  • The compare checks only the latest Partition both tables hold: name others in PARTITIONS.
  • A Script tag, <PARM="NAME"/>, is a Decision: answer it under "tags", as Hive text or a Run value's function.
  • A table that reads itself is seeded once from its original: a "seed" answer limits the Partitions it copies.

Hand-offs

  • From references: a Table reference for each table its scripts read.
  • From excel: the workbook itself, or its Hive from Copilot saved as .hql files beside it, as one batch.
  • On to promote: tables in dev, each Decision made and each compared.

promote

Carries Saved tables from your Dev Database to your Prod Database.

Its notebook: admin/workflows/promote/promote.ipynb. Its names cell: TABLES.

Starts from

  • dev Table folders, each Decision made and compared
  • your Prod Database's name

Ends with

  • prod Table folders
  • each written in prod
  • each in the Reference sheet

Its steps

  1. Promote each table: a prod copy of its folder and Table referencefiles only
  2. Answer each prod table's open Decisions in the decisions cellyour decision
  3. Write each answer into its prod table's Table referencefiles only
  4. Create each table in prodcalls the warehouse
  5. Seed each prod table that reads itself, once, from its originalcalls the warehouse
  6. Write each table in prodcalls the warehouse
  7. Refresh the Reference sheet and the Database modulesfiles only

Common tripping points

  • Fill in PROD in admin/databases.py first: each prod table's location is placed under its location_root.
  • It takes finished tables in dev, each Decision made: TABLES left [] promotes every one not promoted yet.
  • Its decisions step may have nothing to answer, each location placed for you: run on.

Hand-offs

  • From new_table: tables in dev, each Decision made.
  • From convert: tables in dev, each Decision made and each compared.
  • On to schedule: Saved tables, for a run to write on your scheduler's timetable.
  • On to change_a_saved_table: a Saved table in the warehouse, to change with an Admin statement.

schedule

Makes a Scheduled run, a notebook an outside scheduler runs top to bottom, from admin/templates/scheduled_run.py: you fill in its cells in its own notebook, in scheduled_runs/.

Its notebook: admin/workflows/schedule/schedule.ipynb. Its names cell: NAME.

Starts from

  • the Scheduled run's name

Ends with

  • the Scheduled run's notebook

Its steps

  1. Make the Scheduled run's notebookfiles only

Common tripping points

  • The run's notebook has a Build cell, which prints the Hive and sends nothing, and a Run cell, which sends it: read the Build's Hive first.
  • Give each value the scheduler passes in a type hint and a default: one left empty whose hint has no | None is refused.
  • A value the scheduler passes in reaches only the Statements the run hands it to: work out its days in statements() and pass them plain, such as write_days(str(monday), str(sunday)), or give a write the build adds its value with run_values= in the Build cell.

Hand-offs

  • From promote: Saved tables, for a run to write on your scheduler's timetable.

change_a_saved_table

Changes a Saved table in the warehouse with one of the admin module's Admin statements, each logged in admin/admin_log.md.

Its notebook: admin/workflows/change_a_saved_table/change_a_saved_table.ipynb. Its names cell: TABLE.

Starts from

  • a Saved table
  • the change wanted

Ends with

  • the change sent
  • the change logged

Its steps

  1. Write the Admin statement for the changeyour decision
  2. Print its Hive, and run the check its Check first line namescalls the warehouse
  3. Send it, then any check after it, such as admin.check_the_copycalls the warehouse

Common tripping points

  • An Admin statement is a change to a Saved table itself, such as dropping some of its Partitions: write yours in step 1's cell.
  • Read the Hive step 2 prints, and what its check shows, such as the table's Partitions, before step 3 sends it.
  • A where= takes a Condition, such as equals(table.dt, "2026-09-24"): step 1's cell imports equals and between.

Hand-offs

  • From promote: a Saved table in the warehouse, to change with an Admin statement.

upgrade

Carries the Project's files to the Toolbox you copied in, once you have restarted the kernel.

Its notebook: admin/workflows/upgrade/upgrade.ipynb. It has no names cell.

Starts from

  • a Project at an older version
  • the new Toolbox copied in

Ends with

  • the Project at the new version
  • every UPGRADE mark dealt with

Its steps

  1. Upgrade the Project's filesfiles only
  2. Make each change an UPGRADE mark asks for, and delete the markyour decision

Common tripping points

  • Copy in the new sqlglot_composer folder whole, then restart the kernel before step 1: until you do, it still holds the old code.
  • Each UPGRADE mark names a change only you can make: make it, then delete the mark.

Hand-offs

None: run it on its own, whenever you copy in a new Toolbox, before any other Workflow.
